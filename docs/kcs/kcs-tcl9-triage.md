# KCS: Triaging Tcl 9 correctness failures

> **Audience:** Contributor
> **Type:** Issue

## Applies to

tcl-lsp CLI, compiler, runtime, test-suite

## Question

How do I read the Tcl 9 correctness report, classify each failing
test file, and pick the next fix?

## Symptoms

- `make test-tcl9` reports one or more failing test files.
- `tmp/tcl9-report.json` lists per-file results with a category
  letter (A–E) or `pass`.
- The triage table below is stale or missing rows after a fix lands.

## Answer

1. Run `make test-tcl9` locally. This emits
   `tmp/tcl9-report.json` alongside the pytest output.
2. Run `make tcl9-triage` to refresh the table below. The script
   `scripts/tcl9_triage_report.py` rewrites only the region between the
   `TRIAGE-BEGIN` / `TRIAGE-END` fences; prose outside the fences is
   preserved.
3. Pick the highest-blast-radius failing file in category **A** (or
   **B** if A is empty). See the category definitions below.
4. Before you fix anything, add a focused regression test under
   `tests/bytecode_snippets/` and a pytest that exercises it. The
   targeted test should fail at HEAD and pass after the fix.
5. Implement the fix in runtime (`runtime/zig/…`) or compiler
   (`core/compiler/…`). Cite the relevant design doc under
   `docs/design/compiler/` if the fix changes a contract.
6. Re-run `make test-tcl9` and `make tcl9-triage`. The failing
   file's row should flip to `pass` (or, for partial fixes, the
   failed-count should drop).
7. Run `make prep-pr`. Commit the fix; refresh the triage table as a
   separate `chore(triage): …` commit.

### Triage categories

| Letter | Meaning | Who fixes |
|---|---|---|
| **A** | **Runtime bug.** The test file compiled and ran, but produced wrong results (non-zero `failed` count from tcltest). | Runtime / codegen. Highest priority. |
| **B** | **Compiler / emitter bug.** Bundle failed to compile, or the compiled WASM trapped before tcltest could report a summary. | Compiler. Fix after A unless it blocks many A-category tests. |
| **C** | **Unnecessary fallback.** Compilation succeeds, result is correct, but the compiler emitted a `tcl_eval` fallback in a proc that uses no barrier commands (no `uplevel`, `upvar N`, `eval $dynamic`, frame-inspecting `info`). Inferred from compiler-explorer logs, not from tcltest output. | Compiler. Lower priority than A/B. |
| **D** | **Deferred-by-design.** Test file is on the deferred list (I/O, sockets, threads, fs, encoding, platform-specific). | Not fixed in this effort. See [kcs-tcl9-test-corpus.md](kcs-tcl9-test-corpus.md). |
| **E** | **Test infrastructure / tcltest viability.** Includes regressions in `tcltest.tcl` itself, missing `tcltest` plumbing commands (`makeFile`, `cd`), or tcltest summary lines that could not be parsed. | Opportunistically, when it unblocks A/B. |

### Priority rule

Attack order within each category: **A → B → C**. Inside a category,
sort by blast-radius — the number of other failing files whose failure
plausibly cascades from the same underlying bug. The `Subsystem`
column in the table below is the first-order blast-radius proxy; a
bug in `list` typically tags `list`, `dict`, `string`, and `cmd-dispatch`.

### Blast-radius hints

- **list-element quoting / `Tcl_Obj` serialisation** → list, dict,
  cmd-dispatch, string (format/scan).
- **`expr` parsing or evaluation** → expr, control (loop conditions),
  parsing.
- **Error-message format and `-returnCodes` matching** → every file
  with a `-returnCodes error -result {pattern}` test, which is most
  of them.
- **Command-substitution and quoting round-trip** → parsing, eval,
  subst, and any file with inline `[…]` results.
- **`return -code`, `errorInfo`, `errorCode`** → control, proc, eval.
