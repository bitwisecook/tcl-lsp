# KCS: Why does the smoke fallback reject or miss a test?

> **Audience:** Contributor
> **Type:** Issue

## Applies to

tcl-lsp-cli

## Question

Why does `make smoke` or `make smoke-p` fail when cargo-nextest is unavailable?

## Symptoms

- The gate reports a missing, stale, or ambiguous smoke-target manifest row.
- The output says that `cargo-nextest` is unavailable and starts
  `cargo xtask smoke-targets`.
- A smoke test runs with nextest but is absent from the fallback, or the
  fallback refuses to run it.

## Answer

The fallback is deliberately fail-closed. It reads
`scripts/dev/smoke-targets.tsv`, which records the Cargo target that owns each
smoke source. This keeps plain Cargo execution aligned with nextest and avoids
silently running a smaller check.

1. From the repository root, run `cargo xtask smoke-targets check`.
2. Add or correct the one manifest row for each reported source and target.
   Keep the package, target kind, and target name exactly as Cargo reports them.
3. Run `make smoke` again. For one package, use `make smoke-p P=<crate>`.
4. If the check passes, the fallback prints the selected Cargo targets and
   runs their smoke tests. Install `cargo-nextest` only if you want the usual
   nextest runner; it is not required for a correct smoke gate.

Do not remove a row to make the check pass. A smoke test generated by an
attribute macro or an unresolved `include!` expression needs the exact
standalone `// tcl-lsp-smoke-target` line-comment marker on its declaring
source, as described by the
[test-tier contract](../design/contracts/test-tiers-and-ci-gates.md). Marker
or include text inside a string or comment does not count. The check covers
lexically present invocations nested in macro bodies and expressions as well
as item-level invocations. An unresolved include is either non-literal or a
literal file that does not exist until a build script generates it. If another
macro constructs the `include!` only during expansion, treat it like any other
macro-generated test and mark the declaring source as smoke-bearing. A source
with exactly one unresolved include that is known to generate no tests instead
needs the exact standalone
`// tcl-lsp-no-smoke-include` classification. Do not use that classification
for a source with multiple unresolved includes; split the data include or mark
the whole target as smoke-bearing.
