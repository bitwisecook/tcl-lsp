# #1657 bounded hover trace

A bounded native stdio probe used a debug server built from `29dd8ddea3addfa0543b76704b302461f5ad3bad`, with the owner-equivalent Explorer `Arc<CommandBindingRealm>` correction later published as `33cf8caf2` and a local, opt-in hover trace. The complete build diff SHA-256 was `d8c72c236d794328b2f2ca2b8046afe489c3c46fd5fffea2ea2a7c43f3c82368`; the executable SHA-256 was `061d920d898756bdfd65069dba033e07edab2fb88ec25e41035aaaa6d7a2d861`. The trace was enabled with `TCL_LSP_DEBUG_1657_HOVER=1`. It sampled the existing telemetry from a separate thread without acquiring production locks.

The probe first waited for `workspace/symbol` to return an on-disk `lsp1657_ready_fixture`, then opened eight `.brp` buffers containing `# tcl-dialect: probe` and `myblock {set value 1}`. It created a SpecTcl pack defining the `probe` environment, `.brp` extension and `myblock` Body role, sent the watched-file notification, applied a configuration change, and changed all eight buffers. The first hover on `myblock` exceeded 15 seconds. During that wait, a document-free `tcl-lsp.getEffectiveConfig` answered in 4 ms. The run stopped before pack removal; it did not exercise VS Code association ownership.

Five debug samples, taken five seconds apart, showed the hover in `analysis_for` twice, the original-source-view route once, and `cross_document_hover` twice. At every sample the edit order had served its target, no edit held the turn, and the document map and workspace index were free with no recorded waiters. These snapshots do not identify the inner `cross_document_hover` operation.

A second run of the same binary and input repeated the timeout, with document-free configuration answering in 24 ms. `/proc` samples taken every two seconds showed a thread accumulating 199, 199 and 198 CPU clock ticks over consecutive approximately two-second intervals during the late hover window; `CLK_TCK` was 100. This is approximately one core of continued process work, but the samples do not prove that this thread performed the hover's work. Both runs overlapped other system activity and are not latency benchmarks.

The result is an unresolved, reproducible document-response delay on this bounded input. It does not show the reopened issue's historical whole-server, zero-CPU wedge or identify its missing workspace-index holder. The production admission change remains a mitigation; this evidence does not support closing #1657. No lock ordering was changed. The probe, complete logs and sampled process data are retained as `/tmp/lsp-1657-fine-probe.py`, `/tmp/lsp-1657-fine-{result.log,stderr.log,messages.jsonl}`, and `/tmp/lsp-1657-cpu-{result.log,stderr.log,samples.jsonl,messages.jsonl}` for this session.
