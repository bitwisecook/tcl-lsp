# naming.variable.ordered-compiler-primary-cell

Kind: `implementation-contract`

## Problem statement

A compiler can choose an earlier counted local primary under its independently selected comparison rule. Resolving the requested spelling as a runtime name loses that selection; an incomplete lexical write list cannot supply ordered compiler ownership.

## Question

How does a complete source compiler inventory select a counted primary before exact variable cell, alias and lifetime resolution?

## Conclusion

A private compiled-primary receipt is issued only from the complete authenticated ordered source-local inventory at the actual source/configuration/frame and compilation context. Its first counted primary is passed to the existing variable resolver before aliases, TclOO declared-variable matching, observers and exact-cell generation are checked. Runtime DynamicName uses its separate name projection. A missing or large-index result in an owned inventory abstains; independently sound complete-formal-prefix and byte-unique paths remain available when the broader compiler inventory is absent. The source receipt does not grant a physical CPP slot, successful read/write or Normal completion.

## Scope

Rust source-conditional correspondence for independently selected C/Jim compiler models. The test uses genuine counted native-source C8.6 procedure compilation to distinguish k\x00a/k\x00b compiler selection from counted runtime addressing, wrong compilation and unknown-link withdrawal. No native provider execution is attached to this implementation record. Unsupported attempts and large-index fallback remain the ordered producer or instruction owner obligations.
