# naming.vendor.original-source-declaration-consumers

Kind: `implementation-contract`

## Problem statement

Hosted F5 source declarations can retain exact original words while their literal units remain unavailable. Discarding them loses direct source cards, while fabricating C/Jim keys or reusing reporting maps would grant an unrelated lookup, completion spelling or editable declaration.

## Question

Do direct hosted declaration consumers retain genuine source headers and independently current producer/context/roles without converting unavailable literal units into Native naming or edit authority?

## Conclusion

The hosted declaration facade authenticates complete source/configuration and every retained procedure, class or Registry symbol header. Direct cursor selection uses its original source extent and selected role. Source labels come from supported vendor literal units or exact original content spelling; unsupported units remain owned readonly cards. Fresh source-word suggestions require supported units, unchanged full grammar and an independent parse reproducing the same vendor units. Procedure tools, outline, semantic roles, completion and direct header hover/definition consume the same retained source metadata rather than reporting maps. These headers supply no C/Jim recipe, canonical slot, call resolution, runtime cell/class, measured appliance build or edit permission. Missing Native input and unavailable hosted units cannot reopen lexical compatibility.

## Scope

Rust direct hosted source declaration assistance under actual independently selected vendor contexts, including opaque source card spelling and Registry-selected event declarations. Whole consumer image/configuration and selected producer/role remain required. Direct header navigation is distinct from call navigation; readonly cards do not issue a runtime publication. Native provider observations, generated command availability and passing Rust executions are separate questions.
