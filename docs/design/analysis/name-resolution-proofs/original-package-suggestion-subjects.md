# naming.core.original-package-suggestion-subjects

Kind: `implementation-contract`

## Problem statement

A package hint can be suggested for a displayed head even after aliases, stale source or message-only diagnostics disconnect it from the emitting call. Textual package-require scanning also misses escaped original package values and can conflate opaque package keys. A reviewed loading suggestion needs its genuine unresolved subject and canonical package-purpose keys.

## Question

Do package suggestions retain the genuine original unresolved head/lookup and canonical source package requirements instead of reconstructing evidence from reporting strings?

## Conclusion

Known original heads require exact current Input, positioned lookup and the emitting W123 UnresolvedCommand subject with the same Key and lookup. A bounded fixed-ASCII catalogue hint is compared against the selected native command geometry; it proves neither a loader nor callable command. Existing requirements are compared by SourcePackageName NativePackageNameKey, while missing original source operands withdraw the answer. Text ContextDiagnostic ranges and messages cannot supply an original issuer.

## Scope

Original static command heads under a selected native recipe and a genuine typed unresolved diagnostic. Readonly computed or expanded heads do not acquire this static suggestion. Source key and policy, package loading, catalogue assistance and actual command presence remain independent. Logical-only profiles retain their explicit bounded legacy advice. Jim flat keys are not reparsed as C namespace holders.
