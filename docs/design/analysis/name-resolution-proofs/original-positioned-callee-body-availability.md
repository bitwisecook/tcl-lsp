# naming.compiler.original-positioned-callee-body-availability

Kind: `implementation-contract`

## Problem statement

Opaque-callee name effects can be incorrectly closed by a final population of reporting procedure/class/alias/stub/factory names or namespace tails. A future declaration or a donated object label does not identify the implementation body at an earlier original invocation.

## Question

How does local body availability use the actual original IR invocation and independently proved target rather than a reporting-name union when classifying opaque callee arguments?

## Conclusion

UnitCommandResolver receives the complete original Statement and its retained source binding. A Registry-backed proved execution target must retain its authentic identity in the actual Registry generation/context. A non-Registry procedure must retain an implementation allocation site matching a canonical original procedure declaration. Missing Native target correspondence remains opaque even if a later declaration, stub, class, alias, manufactured-instance label or same-tailed name exists in reporting maps. Reporting procedure names and nominal Registry lookup are consulted only after positively retained Logical source naming selects that compatibility purpose. collect_positioned_opaque_callee_name_args supplies each original call/barrier to the resolver and retains literal variable-name candidate arguments for unresolved local bodies; dynamic command heads retain their independent barrier. Local body availability supplies no proof that the callee has no name effects, entered frame, Native execution, successful binding, Normal completion or edit authority. Reporting procedure compatibility requires shared positive retained Logical eligibility and canonical lexical QString candidate qualification. Missing retained input withdraws that branch even when a copied advice flag or procedure report table remains populated. Original positioned Native source-body ownership stays independent.

## Scope

Current Compiler local-body availability and opaque-callee argument assistance in top-level, procedure, method and script-body diagnostic paths. Two fixed source controls verify Native refusal and positive Logical compatibility; existing interprocedural behavior remains independently bounded. No Rust execution receipt or native provider result is attached.
