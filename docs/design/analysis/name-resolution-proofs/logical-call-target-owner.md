# naming.core.logical-call-target-owner

Kind: `implementation-contract`

## Problem statement

A call-hierarchy item can report the same joined title for distinct procedures or member-table sides. Reconstructing a target from that title, kind text or colon splitting loses original declaration boundaries and can hide withdrawn source owners.

## Question

Does the shared Logical call target select one exact actual current declaration range, retain Procedure or Member with independent MemberSide, preserve original direct selector/current workspace owners, and refuse missing, foreign, stale, ambiguous, Native or hosted inputs without reconstructing from presentation labels?

## Conclusion

The current source/API contract selects a unique actual declaration name-token range through the complete current source owner and positive Logical purpose. Typed Procedure/Member and independent MemberSide drive local and workspace consumers, while direct written selector, source alias/rename lineage and actual external visibility remain separate guards. Fifteen linked source controls define finite coverage of the typed target and source-advice ingresses; all are unrun on a matching owned image here. All seven external providers are not tested. No entered dispatch, Native target identity, physical frame/Method record, editing permission or performance result follows.

## Scope

Current shared Core LogicalCallTarget, original class-selector geometry and actual Server workspace handoff. Complete original source/input/store/configuration, exact unique declaration range, typed procedure/member/table side and independent each-document owner are retained. Copied titles, detail/kind labels, joined names and matching ranges under Native/hosted purpose cannot supply the target. Constructor/destructor caller-frame inventory is descriptive source advice, without physical frame entry. Fifteen actual per-body question/document pairs cover finite software definitions only; full provider and current Rust execution outcomes are absent.
