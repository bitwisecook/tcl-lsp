# naming.refactor.original-exact-case-source

Kind: `implementation-contract`

## Problem statement

Independent switch consumers can reconstruct option and case layout or cook a subject label into new source, losing authentic aliases, literal values and original subject syntax. General exact-case layout and data-group scalar classification need distinct source receipts.

## Question

How do source consumers share selected exact, case-sensitive effective case ordinals, literal case data and arbitrary original subject syntax while keeping scalar classification and rewrite permission independent?

## Conclusion

OriginalExactCaseSource selects the actual Registry case descriptor through complete original analysis, source image, retained Realm/config and effective argv. It preserves an arbitrary genuine subject NativeWord and completed literal pattern/body data. OriginalExactSwitchSource independently projects exactly one scalar substitution for data-group advice. Dictionary conversion reproduces original subject syntax and literal pattern values under the same selected grammar; aliases, options, shadows and source currency remain guarded. A positive Native source receipt still returns the existing disabled rewrite obligation. These source/API controls establish layout and lexical completeness only, without entered matching, body evaluation or runtime equivalence.

## Scope

Three marked controls retain genuine literal, compound and array subject syntax; exact/case-sensitive option and inline/list case layout; completed dollar/bracket/space data; authentic selected aliases and bound effective argv; known shadows and missing/stale input/config refusals. Explicit Logical editing eligibility remains separate. The general carrier supplies no scalar variable classification, native receiver/current read, new temporary cell, Native execution, frame, insertion or movement permission. Generated source syntax checks are lexical only. All seven external providers are not tested for this implementation contract.
