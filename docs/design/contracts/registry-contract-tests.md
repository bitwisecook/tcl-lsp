# Registry contract tests and golden fixtures

This contract describes the **language-agnostic shape contract** for the
command registry and the iRules event / profile / object graphs, and the
front-end-driven tests that enforce it.  The goal is that a future Rust
front-end (the `rust` branch) can be validated against the *same* golden
fixtures without sharing any Python: the contract is the JSON shape a
front-end emits, not an internal API.

## Layers

The work is two layers, both driven entirely through the front-ends.

### 1. Bulk shape contract — `registry-dump` verbs + golden fixtures

Two front-end verbs serialise the registries as canonical JSON:

- `tcl registry-dump [--dialect D | --all-dialects]` — the command
  registry: every command with its arity, switches, forms, subcommands,
  and **every boolean trait** on `CommandSpec` (captured automatically,
  so new traits need no test edit), plus a curated set of scalar traits.
- `f5 registry-dump --section {commands,events,profiles,objects,all}` —
  the F5 command registries and the event, profile, and object graphs.

Both verbs are thin wrappers over
[`tooling/registry_snapshot.py`](../../../tooling/registry_snapshot.py),
which lives in the front-end (`tooling/`) layer because it must reach
both `compiler.registry` and the BIG-IP object graph in
`dialects.f5.bigip` (`compiler/` may not).

The committed golden fixtures live under
[`tests/baselines/registry/`](../../../tests/baselines/registry/), one
file per dialect plus `events.json`, `profiles.json`, and `objects.json`.
They are regenerated by
[`scripts/codegen/registry_baselines.py`](../../../scripts/codegen/registry_baselines.py)
(`make gen-registry-baselines`); `--check` (`make check-registry-baselines`,
and the `test_registry_fixtures_are_not_stale` pytest) fails on drift.

`tests/registry_contract/test_registry_dump_snapshot.py` runs the verbs
(in-process, and once as a real subprocess) and asserts their output
equals the fixtures.

### 2. Behavioural contract — real front-end behaviours

Anything a real, user-facing front-end behaviour surfaces is tested
*through that behaviour*, not via the bulk dump:

- `tests/registry_contract/test_command_info_behaviour.py` drives
  `tcl command-info --json` for **every command in every dialect** and
  checks summary, synopsis, switches, and the events-validity matrix.
- `tests/registry_contract/test_event_info_behaviour.py` drives
  `f5 irule event-info --json` for **every known event**.
- `tests/lsp_e2e/test_registry_contract_e2e.py` drives the LSP
  `workspace/executeCommand` registry handlers
  (`describeIruleEvent`, `describeIruleCommand`, `listIruleEvents`,
  `listSubcommands`).  Because the e2e harness honours
  `TCL_LSP_SERVER_KIND=rust`, this layer becomes the cross-language
  contract automatically.

## Content-addressed cross-products

Two registry facts are full cross-products and would bloat the fixtures
to tens of MB: the commands valid in each event, and the events each
command is valid in.  The fixtures store a **count plus a sorted-list
SHA-256 digest** (`digest_list` in `tooling/registry_snapshot.py`)
instead of the verbatim lists.  The behavioural tests reconstruct the
full list from the live `command-info` / `event-info` front-end output
and verify the digest — so the exact content is covered, not just the
count, while the fixtures stay small.  The digest sorts before hashing,
so a front-end need only emit the same *set*, in any order.

## Stable wire conventions

- Enums serialise to their **symbolic name** (e.g. `INLINE`), never an
  `auto()` integer, so the wire form is reproducible without copying
  Python values.
- Arity serialises as `{"min": int, "max": int | null}`; `null` max
  means unbounded.
- All fixtures are sorted-key, 2-space-indented JSON with a trailing
  newline (enforced by `test_fixtures_are_canonical_json`).

## When the registry changes intentionally

Run `make gen-registry-baselines` and commit the fixture diff alongside
the registry change.  The diff against the golden files should tell a
clean story; an unexpected churn (lost commands, flipped traits) almost
always means the change is wrong.

## Using the contract from the `rust` branch

A Rust front-end re-implements the `registry-dump`, `command-info`, and
`event-info` verbs (CLI) and the four LSP `executeCommand` registry
handlers, emitting the same JSON shapes.  Point the e2e harness at the
native server with `TCL_LSP_SERVER_KIND=rust`, and run the CLI contract
tests against the Rust binaries; both validate against the unchanged
fixtures in `tests/baselines/registry/`.
