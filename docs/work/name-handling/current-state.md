## Performance (release blocker)

**Per-edit CPU and memory are not release-acceptable.** Measured on a 30-line, three-procedure file (`ci` profile, `tcl-lsp-db` `edit_memory` and `tcl-compiler` `per_item_fallbacks` examples, callgrind/DHAT): one cold analysis cost 3.88 G instructions (~0.6–0.8 s), an edit ~1 s CPU, and 20 edits reached 620 MiB RSS. DHAT showed only 16 MB live at exit but a 334 MB live peak and ~1 GB allocated per analysis; the RSS is that transient peak, not retained salsa state (salsa memos totalled kilobytes).

Causes found:

- The per-item fast path never runs: `fragment_needs_original_source_owner` falls back for any body carrying `original_conditional_registry_metadata`, i.e. any body with `if`/`for`/`while`. Every edit therefore re-analyses the whole document after first paying for the shell walk. Unlocking it needs a rebase of that metadata's source receipts (open).
- The fallback analyser rebuilt the CFG/SSA compilation unit the db had already supplied, rebuilt the document realm the shell had already built, and dropped the driver's file path, version, declared-target and workspace-class settings.
- Naming lookups recomputed the same projections repeatedly: per-point dispatch bindings (~37× per command per analysis), token stamping (~2,800×), `[…]` substitution re-lowering for SCCP, and one-element `BTreeSet<MayBinding>` baseline rows (~1.5 GB of the 7.2 GB allocated over six edits).
- Flow state was deep-copied per program point: namespace/cell/name sets in `ResolveContext`, binding namespace lists and the source command world's namespace rows; registry semantic keys compared whole command inventories when `Arc`s differed; version strings were re-parsed into heap vectors on every registry lookup.

Real files are far worse than the 30-line sample. On the Tcl 8.6 library (24 files, `per_item_fallbacks` corpus run), fallen-back documents averaged ~10–15 s per analysis: `tcltest.tcl` (3,600 lines) 44 s, `clock.tcl` 42 s, and the 377-line `http1.0/http.tcl` 46 s (105 G instructions). Sixteen of 24 files fall back: nine for `enclosing-context` (81% of lines) and seven for the conditional-metadata ownership gate. With that gate skipped in a probe, all seven take the fast path, so it is the only blocker for them. Super-linear causes found by stack sampling and callgrind: a new realm (with empty advice caches) built per command from lowered modules, re-preparing the whole-program advice tape each time; and qualified-variable name lookups joining every earlier site's binding per query instead of using the realm's site memo.

Adopted (`work`): `d57c2d639` (fallback reuses the supplied unit and shell realm under an exact input check and carries the full analyser configuration; memoised point dispatch bindings, realm token stamping and SCCP substitution touches; interned registry semantic keys; copy-on-write cell/namespace/name sets and namespace ledger with a first-row index; shared namespace lists; borrowed/shared baseline binding rows; inline version segments) and `232a479dd` (one shared document realm per lowered module). Measured: 30-line cold analysis 3.88 G → 3.29 G instructions, 20 edits 20.4 → 16.3 s CPU and 620 → 410 MiB peak RSS; Tcl library total 236 → 160 s, `auto.tcl` 17 → 4.7 s, `http.tcl` 46 → 15 s. Validation for each: every `tcl-compiler` lib test compared against the HEAD baseline with a crash/timeout-bisecting runner (baseline fails ~2,000 of 10,870); no regressions, and two former timeouts pass. One origin-sharing change was reverted because it broke per-origin memo identity. `tcl-registry` matches its 11 baseline failures; `tcl-dialect` passes. Still far from lightweight.

In validation: realm query memo for written-name lookups, shared whole-program advice tapes across realms, prefix-max pruning of written-word sites (`http.tcl` ~10 s).

Next: unlock the per-item fast path (rebase conditional-metadata receipts; then `enclosing-context`); remove the remaining duplicate source-binding walks (CU lowering, shell, whole-file command trust); FxHash for hot sets (SipHash on `VariableCellKey` is ~25% of `http.tcl`); intern `SourceNamespaceKey`/`ByteNamespacePath`; evaluate a size-class allocator for the server binary (jemalloc measured ~18% CPU); consider a per-analysis arena once copies are gone.
