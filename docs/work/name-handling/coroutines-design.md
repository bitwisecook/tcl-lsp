# Coroutines and tailcall

How `coroutine`, `yield`, `yieldto`, `coroinject`, `coroprobe`, `info coroutine` and `tailcall` behave in the engines, and how analysis, navigation and the optimiser model them. It extends the coroutine and `tailcall` rows of [call frames](frame-design.md) (fixtures `fr06`, `fr07`) and feeds decision 2 ("coroutine" as an entry context) and decision 8 (the potential-execution owner) of [design integration](design-integration.md).

**Question and method:** do the engines run coroutines and `tailcall` as C Tcl does, and does analysis give coroutine programs correct answers? Thirteen fixtures in [`oo-dispatch-probe/coroutines/`](handover/oo-dispatch-probe/coroutines/) (generators, resume arity, `info coroutine` in namespaces, the coroutine frame, rename and deletion from outside and inside, `yield` outside a coroutine, `coroinject`/`coroprobe`, `tailcall` from a procedure, lambda and method, `tailcall` inside `catch`, a coroutine over `apply`, `tailcall` inside a coroutine) ran under tclsh 8.4.20, 8.5.19, 8.6.18, 9.0.4 and 9.1.0, Jim, the VM (`tclvm --tcl-version 8.6|9.0`) and the Rust runtime (`run_script --quiet`, native build) on `afe2f2d8`; results in [`engines.tsv`](handover/oo-dispatch-probe/coroutines/engines.tsv). The same files went through the MCP `analyze`, definition, references, hover, rename and optimiser tools (a cached build that may lag `afe2f2d8` slightly); results in [`analyser-mcp.out`](handover/oo-dispatch-probe/coroutines/analyser-mcp.out). The code census is a read-only grep of production code with the decisive lines read.

**Verdict:** the engines are **right**: every fixture prints what tclsh prints on 8.6 and 9.0, bar two `wrong # args` texts. Analysis has **no coroutine model at all**. A coroutine body is analysed as an ordinary procedure, the coroutine command is a name with no declaration, no signature and no frame, and `yield` is an ordinary command. That gives a false W241 on every generator, a false W123 whenever the coroutine is created inside a command substitution (the common `puts [coroutine c gen]` and `set first [coroutine c gen]` forms), no definition or hover for the coroutine command, and no arity check on resumes. `tailcall` is modelled correctly as a frame-replacing exit through the registry's `REPLACES_FRAME` trait.

Jim has no coroutines; its `tailcall` matches Tcl for procedures and lambdas, and refuses a method (`tailcall can only be called from a proc or lambda`). 8.4 and 8.5 have neither command, and the analyser reports W002 there.

**The substitution case is isolated by one pair** (in `analyser-mcp.out`): `coroutine top g; top` is clean, `puts [coroutine nested g]; nested` and `set r [coroutine nested2 g]; nested2` are W123, while `set z [proc made {} {}]; made` is clean. The registry states that `coroutine` publishes the command named by its first word (`defines_command_at: Some(0)`, `rust/tcl-registry/src/commands/tcl/coroutine.rs:75`), but only the top-level publication path honours it for `coroutine`; `proc` reaches publication by another route (inference: `authored_source_command_publication`, `rust/tcl-registry/src/resolved_invocation/source_definitions.rs:239`, is only consulted for statement-level invocations).

**Navigation:** go to definition and hover on a resume of `c` return nothing. References to and rename of the body procedure include the `coroutine c counter 5` word, because `coroutine` declares a command prefix at argument 1 (`coroutine.rs:83`). The optimiser leaves generator code alone.

**What the runtime result means:** `run_script` here is the native build, where coroutines run on OS threads. In the wasm32 build that the compiler targets every coroutine command refuses (`coroutines are not supported in the single-threaded wasm build`, `runtime/rust/src/cmd_coro.rs:956-1020`).

## Census

**Engines (two complete implementations):**

- VM: `rust/tcl-vm/src/cmd_coro.rs` (1245 lines). It holds `coroutine`, `yield`, `yieldto`, `coroprobe`, `coroinject` and `::tcl::unsupported::corotype`, keeps resume arity in `validate_resume_arity` (`:354`, its own `?arg?` text), and tracks rename and deletion by fully qualified name (`on_command_renamed`, `:212`). `tailcall` is at `rust/tcl-vm/src/command.rs:1097`. A fourth, iRules-only path keeps coroutine activations for TMM timers (`rust/tcl-vm/src/retained_activation.rs`).
- Runtime: `runtime/rust/src/cmd_coro.rs` (1480 lines), with a thread backend and a wasm32 refusal stub. Resume arity is in `coro_resume_command` (`:896`, its own `?value?` text, `:917`), and rename and deletion are tracked by command generation (`:929`, `:938`). `tailcall` is at `runtime/rust/src/cmd_control.rs:425`.
- Shared: coroutine name publication (`tcl_syntax::naming::native` `CoroutinePublication`, `command_slots.rs:219`, `routing.rs:291`), used by both engines; the compiled coroutine recipes (`rust/tcl-registry/src/native_coroutine_compilation.rs`), used by codegen (`rust/tcl-codegen/src/codegen/native_coroutine.rs`) and analysis preflight (`command_binding/compiled_preflight/original_preparation.rs:214`); `NativeCoroutineResumeArity` (`native_coroutine_compilation.rs:406`), which the engines do **not** use for the arity error text. `tcl-runtime-api/src/retained_activation.rs` (65 lines) is the only trait-level surface.
- Disagreements: two resume-arity texts (only the VM's matches C); two `coroutine` usage texts (only the runtime's matches C; the VM copied the registry synopsis); two identity schemes for the live coroutine (name against generation).

**Registry:** specs `coroutine.rs`, `yield_.rs`, `yieldto.rs`, `coroinject.rs`, `coroprobe.rs`, `tailcall_.rs`, `info_.rs` (`info coroutine`, `:996`). The traits are `COROUTINE_PRIMITIVE`, `TRANSFERS_CONTROL` (`yield`, `yieldto`) and `REPLACES_FRAME` plus `TRANSFERS_CONTROL` (`tailcall`). The `coroutine` spec's comment says a resume takes "any number of values" (`coroutine.rs:78-82`). That holds only after `yieldto`; after `yield` the limit is one value, as co02 shows. The arity is declared `Unknown` on purpose, so nothing checks it.

**Analysis and LSP:**

- `COROUTINE_PRIMITIVE` has exactly one production reader, `rust/bpf-tcl-ir/src/lower.rs:266`. Nothing in `tcl-compiler`, `tcl-lsp-core` or the server reads it.
- There is no coroutine variant in any analysis frame type (`VariableExecutionFrame`, `FrameContext`, `BodyFrame`; see [call frames](frame-design.md)), and no entry context, so a coroutine body is analysed as a procedure entered from its caller.
- `info coroutine` is classed as frame-inspecting by escape analysis (`var_escape/info_subcommands.rs:53`, `slot_resolution.rs:778`). Hover has a release row for it (`tcl-lsp-core/src/hover/original_registry.rs:949`).
- W241 decides "leaves the loop" from `TERMINATES_BLOCK | BREAKS_LOOP | REPLACES_FRAME` (`analyser/bounds_checks.rs:155`). `yield` is none of these, and no rule asks whether the loop is in a coroutine body.
- `tailcall` as an exit: the flow facts (`cfg_builder/flow_facts.rs:53`, `:195`), lowering's `Return` terminator (`cfg_builder/script_lowering.rs:126`) and the inliner (`inline_uplevel.rs:964`) read `REPLACES_FRAME`. The LSP source graph instead reads `TRANSFERS_CONTROL` as "may end load" (`tcl-lsp-core/src/source_graph/sequence_capture.rs:139`), so `yield` and `yieldto` count too, which is harmless at top level but a second rule. That makes **two trait-based rules for "leaves here"**, with no string matching.
- Codegen keeps `[yield]` yieldable in substitutions, `catch` and `try` (`codegen/statements/value_words.rs:352`, `control_flow/catch_command.rs:220`, `try_command.rs:281`).

## Design

- **Registry descriptors** (decision 6): `coroutine` should state a *created command contract* rather than only `defines_command_at`. The contract holds the new command's identity (`CommandRef` with the allocation site of the `coroutine` invocation), its kind (`coroutine`), its resume grammar, and the body it runs: a command prefix whose body unit is entered with a coroutine frame. The resume grammar is "0..1 argument while suspended at `yield`; any while suspended at `yieldto`". `NativeCoroutineResumeArity` already names the two states and should own the error text for both engines.
- **Frames** (decision 2): add the coroutine entry context, which the integration decision already lists. A coroutine frame is level 1, namespace `::` for the base frame (the body procedure then pushes its own frame; co04), and no caller frames are reachable above it. `info coroutine` answers the created identity there, and `{}` elsewhere.
- **Body unit and SSA:** each `yield`/`yieldto` is a suspension point. Locals persist across it (co04), and globals, namespace variables and the name world may change across it, like a call to unknown code. The resume value is the result of the `yield` (unknown, or the union of the arguments at proven resume sites). A suspension inside a loop is an exit for W241's purpose ("control can leave this activation here"), so the rule asks a registry fact — a `SUSPENDS_ACTIVATION` effect or the existing `COROUTINE_PRIMITIVE` — and not a command name.
- **Potential execution** (decision 8): the body procedure of a coroutine is *entered* at the `coroutine` site, and its remaining code is *possibly reached* at each resume site of the created identity. Rename and deletion of the created command end those points (co05, co13). Code after `tailcall` is not reached.
- **Name world:** the created command is a binding in the per-point name world, at nested sites as well as statement sites (decision 4: the annotated command covers every reached command, however nested).
- **Answer with receipts:** definition and hover on a resume return the `coroutine` invocation as the declaration, with a Logical receipt; arity diagnostics on resumes need the suspension kind, which is Unknown unless the body has only `yield`.
- **Conformance:** these fixtures become vectors run by both engines and by the analyser (W123, W241, W211), definition and hover.

## Plan

- **Created command at nested sites.** Owner: command binding (`tcl-compiler/src/command_binding/`) and `rust/tcl-registry/src/resolved_invocation/source_definitions.rs`. Publish the command named by `defines_command_at` for invocations inside command substitutions as for statements, so `puts [coroutine c g]; c` is clean. Done when the discriminating pair in `coroutines/analyser-mcp.out` reports nothing, and co01, co02, co03, co10, co11 and co12 lose their W123s.
- **Generator loops are not W241.** Owner: `rust/tcl-compiler/src/analyser/bounds_checks.rs` (`is_loop_exit_command`) and `rust/tcl-registry/src/traits.rs`. Treat a body word whose command carries a suspension fact (`COROUTINE_PRIMITIVE` on `yield`/`yieldto`, or a new `SUSPENDS_ACTIVATION` effect) as leaving the activation, with no command name in the analyser. Done when co01 and co05 report no W241, and `while 1 {incr i}` still does.
- **One resume-arity owner for both engines.** Owner: `NativeCoroutineResumeArity` in `rust/tcl-registry/src/native_coroutine_compilation.rs`, used by `rust/tcl-vm/src/cmd_coro.rs:354` and `runtime/rust/src/cmd_coro.rs:896`. Give it the C text (`"NAME ?arg?"`), and give the `coroutine` usage text (`coroutine name cmd ?arg ...?`) one owner as well. Done when co02 and co11 match tclsh in both engines.
- **Coroutine created-command contract.** Owner: `rust/tcl-registry/src/commands/tcl/coroutine.rs` and the contract assembly of decision 6. Replace the "any number of values" comment with the two-state resume grammar, and expose the created identity so definition and hover on a resume reach the `coroutine` invocation. Done when definition and hover on `c` in co01 answer, and the analyser reports `c a b` on a body that only `yield`s (warning severity, since the suspension kind is a proof).
- **Coroutine frame and suspension points in analysis.** Owners: the static `Frame` of decision 2 (frame-design plan item 4) and lowering and SSA (`cfg_builder`, `ssa`). Add the coroutine entry context, and model `yield`/`yieldto` as suspension points that keep locals and invalidate globals and the name world. Done when co04's `info exists ::outer` counts as a read (no W211), a global written between resumes is not folded across a `yield`, and the frame fixtures `fr07` and co04 drive the analyser.
- **One "leaves here" rule.** Owner: `tcl-lsp-core/src/source_graph/sequence_capture.rs:139` and `cfg_builder/flow_facts.rs`. Read one registry control fact for "ends the activation" (`REPLACES_FRAME`, `TERMINATES_BLOCK`) and a separate one for "suspends", instead of `TRANSFERS_CONTROL` in one place and `REPLACES_FRAME` in another. Done when both callers share one registry query, with a unit test listing `tailcall`, `return`, `yield` and `break`.
- **Wasm coroutine support or an explicit non-goal.** Owner: `runtime/rust/src/cmd_coro.rs` (the wasm32 stubs) and [backend constraints](../../design/runtime/backend-constraints.md). Either implement coroutines on the explicit-stack evaluator, or record that compiled wasm output refuses coroutines and have the compiler report it at compile time. Done when the decision is recorded and a compile of co01 for wasm either runs or is refused with a diagnostic.
- **Conformance vectors.** Owner: the engine end-to-end suites (`rust/tcl-vm/tests`, `runtime/rust` tests) and an analyser vector runner. Turn the 13 fixtures and `engines.tsv` into vectors run by both engines (8.6 and 9.0), and by the analyser and LSP (W123, W241, W211, definition, hover). Done when a regression in any of the measured rows fails a test.
