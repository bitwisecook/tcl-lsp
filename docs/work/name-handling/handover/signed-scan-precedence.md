# Signed scan values and expression precedence, 20 November 2026

This work landed on `work` between `ab381fa1` and `ec32f8e4`. It adds W154 (operator mix that groups differently from how it reads), W155 (any non-associative grouping, hint, off by default) and W156 (signed `binary scan`/`scan` value compared or consumed as unsigned, replacing IRULE5008), the expression precedence hover tree, the parenthesise and remove-redundant-parentheses refactors, the minifier's parenthesis pass, the anchored-glob F5 `matches` fix in `f5-xc`, and registry integer argument domains (`arg_domains`, SpecTcl `-domain`, vocabulary 2.3).

## Scope

- `rust/tcl-syntax/src/expr/precedence.rs`, `rust/tcl-syntax/src/scan.rs`, `rust/tcl-syntax/src/glob.rs`.
- `rust/tcl-compiler/src/analyser/diagnostics/usage/precedence_hazards.rs` and `rust/tcl-compiler/src/analyser/diagnostics/dataflow/signed_scans.rs` with their tests.
- `arg_domains` in `rust/tcl-registry`, its SpecTcl loader and Spec Studio field.
- `rust/tcl-lsp-core` hover, refactor and minify additions for expression parentheses.

## How to measure

```bash
cargo test -p tcl-compiler --lib -- signed_scans precedence_hazards
cargo test -p tcl-syntax --lib -- precedence glob scan
cargo test -p tcl-registry
```

The first takes about 15 seconds once built. Oracle evidence is in `evidence/tcl/binary-scan-signed-byte-comparison.md`, `scan-integer-signedness.md`, `signed-scan-downstream-consumers.md`, `expr-precedence-groupings.md` and `string-match-bracket-set-edges.md`; BIG-IP facts are in `docs/design/f5/bigip-irule-parser-measurements.md`.

## Queue

1. **Methods versus procedures in the per-function pass.** `CompilationUnit` builds SSA for procedures but method bodies in `cu.methods` get no SSA blocks, so every SSA-driven check (W233, W210, W156) is silent inside `oo::define … method` and `itcl` bodies. Inside procedures, commands after a call the binder cannot prove stay unlowered generic calls behind `<unseen-call>` markers, so SSA names no variable after them; W156 works round this with marker-aware fallbacks (`beside_marker`, `UnresolvedScans`), which other dataflow checks lack. Review which per-function analyses run for each unit kind, give method bodies the same pass as procedures (with `self`/`my` and the object's variables as entry facts), and decide whether lowering should continue past an unproven call rather than each check re-deriving facts. Smallest fixture: `oo::class create C { method m {d} { binary scan $d c b; if {$b == 0x81} {} } }` should report W156 as the same body in a `proc` does. Files: `rust/tcl-compiler/src/compilation_unit/function_build.rs`, `rust/tcl-compiler/src/cfg.rs`, `rust/tcl-compiler/src/analyser/diagnostics.rs`.
2. **TclOO coverage matrix**, measured on `2ad579f4` with `Analyser::analyse` under `tcl8.6` and `tcl9.0`; every fixture was run under tclsh 8.6.18, 9.0.4 and 9.1.0 first (itcl and snit are not installed, so their rows are static only). Each body held a signed-byte comparison (W156) and `$d & 0xff == 1` (W154, purely syntactic).
   - Walked, no SSA (W154 yes, W156 no): `method`, `constructor`, `destructor`, `self method`, `classmethod`, `private method`, `method -unexport` inside an `oo::class create` or `oo::define C {…}` script, `oo::objdefine o {…}` scripts, `oo::singleton`/`oo::abstract` bodies, itcl `method`/`constructor`/`proc`, snit `method`/`typemethod`/`constructor`. Procedures, namespace procedures and `apply` bodies report both.
   - Not walked at all (neither code): the one-member command forms `oo::define C method|constructor|destructor|self method …`, `oo::objdefine o method …` (also on a class object), the 9.0 `initialise` script (which runs immediately, so its errors happen at definition time), and `itcl::body`.
   - False W123 in entered bodies, all clean under tclsh: `my variable`, `my destroy`, `my <forward>`, `my <unexported method>`, `self`, `self class`, and the 9.0 helpers `link` and `callback`. Cause as for the `next` hand-off in `class-facts.md`: the presence query does not see the object namespace or `::oo::Helpers`.
   - Spurious W307 ("non-literal command name") on `[C new]` once the class has `superclass`, `filter`, `private variable`, a later `oo::define C variable`, or a later `oo::define C method`; the same call is silent on a class with only `variable` and methods. This matches the class-facts queue item where every command after `oo::define` becomes unknown.
   - Missed: constructor arity (`C new 1` against `constructor {a b} { list }` raises on every release; method arity is reported as E002), and calls to methods removed by `deletemethod` or renamed by `renamemethod`. A constructor or destructor with an empty body is deleted by TclOO, so `constructor {a b} {}` accepts any arguments; any constructor arity check must honour that.
   - Correct: W002 for `classmethod`, `initialise`, `private`, `-unexport`, `oo::singleton` and `oo::abstract` under 8.6; W120 for `link` and `classvariable` under 8.6; no false positive for class `variable`, `oo::objdefine` `variable`, `classvariable` (9.0), `namespace upvar`, `mixin`, an `unknown` method, or `[namespace which my]` callbacks.
3. **Further TclOO, class-system and dispatch gaps**, measured the same way; fixtures, outputs and the probe are in [`oo-dispatch-probe/`](oo-dispatch-probe/README.md). itcl rows were checked against itcl 4.3.5 on tclsh 9.0.4 and 9.1.0; snit and critcl rows are static only.
   - Calls nested in `catch {…}` or `[…]` lose method checking: `C create o; o m` (too few arguments) and `o nosuch` are reported at the top level but silent inside `puts [catch {o m} msg]`, while `$o m` on a `[C new]` handle is reported in both. This first looked like a named-object fault; the discriminating fixtures show it is nesting (cause 4 of [oo-tk-root-causes.md](../oo-tk-root-causes.md)). `C nosuch` was only measured nested.
   - Object reshaping is not followed: `oo::copy`, `oo::objdefine o class B`, `export`/`unexport`, `superclass -append`/`-clear` slot operations, and calling the unexported `eval` built-in from outside all go unreported; the slot operations also draw the spurious W307. A class with two superclasses (`nextto`) draws it too.
   - 9.0 `oo::configurable` properties: `$o configure -colour 1` on a class whose only property is `size` is silent.
   - More false W123 on `self` (`self next`, `self method`, `self call`) and `my varname`/`my eval`.
   - Namespace ensembles are opaque: wrong arity through `-map`, an unknown subcommand, a non-exported command, and wrong arity with `-parameters` are all silent. A `-map` target is resolved in the ensemble's namespace, so `-map {mk {C new}}` inside `namespace eval ::e` fails as `::e::C` on every release; this is missed. Parameters of an `-unknown` handler draw W214 although the handler signature is fixed.
   - Arity is missed through `tailcall`, a literal command prefix expanded with `{*}`, and a coroutine command (which takes at most one argument). `while 1 { yield … }` in a coroutine body draws W241 (provably infinite), which is wrong for a generator.
   - Handled: `interp alias` arity (E002), a call to a renamed-away procedure (W123), `apply` arity through a lambda variable (E002, though the message counts the lambda's own formals), and no false positives for a user `unknown`, `namespace path`, `namespace unknown`, execution traces or computed `proc` names.
   - itcl: `package require itcl` draws W120 ("requires `package require Itcl`"), but itcl 4 provides both names. Wrong arity and unknown methods on an itcl object, `chain`, and unknown `configure` options are silent.
   - snit: `delegate method … to component` is not modelled; an undelegated call is silent.
   - critcl: no registry or compiler model; commands defined by `critcl::cproc`/`critcl::ccommand` are neither known nor checked.
