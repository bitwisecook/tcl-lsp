# Naming completion plan

**Goal.** One design for command and variable name handling, shared by the LSP, the compiler and analysers, the optimiser and the tools: one identity layer, one lookup owner, one per-site record, one answer type, and registry descriptors instead of command-name special cases. The numbered items below are the work; the design pages they link to are the detail.

**Scope (owner decisions, 23 November 2026).**
- `work` is a long-running design branch with no release target. Fixes reach users through `rust`; `work` releases when the redesign is complete.
- Active: every LSP consumer and the shared compiler, database and registry owners it needs.
- Deferred off this branch: VM and runtime work (engine-only items are listed under the working order), except item 312, the VM's move to a Tcl 9.1 base, which the owner brought forward on 26 November 2026 because serialised bytecode (311) and SpecTcl images depend on it; dialect execution in the engines (Jim, iRules and others: a distant goal), BIG-IP migrations beyond the wrong answers in stage 2, and the licence (item 74, before any release).
- The 2,158-unit migration catalogue is frozen (item 96): it is a cross-check on the phases, not the driver.

**Rules.**
- Keep written source, evaluated names, namespace identity, command slots, live command identity, variable places and display text distinct. A display string never reconstructs identity; repair missing owner transport instead of weakening guards or adding string inverses.
- Oracles: C Tcl 8.4.20, 8.5.19, 8.6.18, 9.0.4 and 9.1.0 with their own `init.tcl` and tcltest, Tk 8.4–9.1, upstream jimsh, and for BIG-IP the build-stamped lab evidence. Vendor files, raw TMSH and schema tables and extracted manuals stay outside the project.
- **Done** means the item's "done when" test runs and passes, and the conformance rows it names (item 205) are green. Source review, a compile check or an assumed behaviour never counts as done.
- Commit coherent, reviewed steps; record failures and checks not run.

**Working order.** Stages run in order; items within a stage can run in parallel. Phase numbers are those of [design integration](design-integration.md#corrected-order).
