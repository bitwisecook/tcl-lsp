# Original Jim catch/try quiet global capture

Question: does the early quiet global `errorCode` getter change the message bound by catch/try, and which actual captured header reaches options?

`capture03` is the completed matrix: original `catch`, `try on error`, and `try on error ... finally`, each with missing, scalar, alias, failed dictionary alias, and normal body completion controls. Its 15 exact inputs and 15 observations are retained in `execution.stdout`; byte fields are hexadecimal. OBS fields are form, mode, raw final code, result, message, options, options-errorcode-is-original-keep, errorcode, handler, finally. A dash means the original API returned NULL. `keep` safely owns the expected original header independently. The probe examines actual pointer identity; it does not reconstruct identity from printed values.

The failed dictionary alias publishes its dictionary diagnostic before the message-variable write. Options omit errorCode when that quiet getter returned NULL. The exact original inputs, source, executable, compiler invocation, streams, completion, linked libraries, and hashes are in each capture. The current upstream HEAD was rechecked at execution time against the local original source. All 247 selected provider inputs were unchanged. The original namespace suite, using its original testing.tcl/tcltest.tcl, passed 79/79.

`capture01` is failed network setup: no compile or semantic execution. `capture02` compiled the broader 25-case output-overwrite matrix but its original process ended with signal 11. Its buffered partial output is retained as failed execution, and grants no complete matrix acceptance; the failure was not diagnosed. `capture03` independently reran the narrower 15-case matrix and completed with exit 0. The root probe and driver are the exact successful capture03 versions; each earlier capture retains its own beforeimage.

This evidence covers the selected built-in catch/try paths in an original interpreter after Core and InitStaticExtensions. It does not establish VM parity, custom getter callback ordering, every native reference stage, ignored codes, signals, or unsafe output-overwrite cases. No Runtime or VM test was executed by this capture. The VM regression compares the observed message/result, selected errorCode identity, and handler/finally reachability; stack-trace presentation is outside that regression's assertions.
